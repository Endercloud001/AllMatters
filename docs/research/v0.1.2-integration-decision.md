## 接受顺序与确认端：用户已确认 Host

用户明确选择“采用推荐：Host 统一接受与确认”。所有玩家包括房主的编辑、改票、取消和断线释放走 Host 同一串行接受流程，房主无旁路写入或编辑优先权。领域 Module 决定合法性和转换，传输 Module 负责送达；客户端按已接受结果更新，不自行扣步或重抽。

Host 根据同一次进入的原生房间就绪结果确认成功一次；返回 Task 完成不单独构成成功证据。确认前失败/取消不扣步，重试沿用已定目的地；确认后客户端加载错误或断线不撤销进入或再扣步。Host 离开结束本局，不增加迁移或热重连。原生就绪观测点与具体 Adapter 接入仍需正式验证；随机职责与恢复粒度已在本文明确。

这项选择承受操作确认的网络往返延迟；最后一票与撤票按同一接受顺序仅产生一个结果。没有要求每端各自确认后独立生效，也没有以所有客户端成功加载作为每次确认的硬前提。既有原生必要同步安全措施保留，不承诺绕过其内部协调。

## 随机职责：独立方案已确认

用户原话：“采用推荐的独立方案。”拼图生成与目的地抽签各有独立、可恢复的 Mod 随机序列，原生战斗/事件/奖励继续使用各自原生机制。生成内部的造池与布局搜索不得消耗目的地流或原生内容流；不在此冻结流名称、类型或拆分数量。

Host 在玩家票列表抽取（不去重）；已确定目的地存入本次操作，失败重试不重抽。已授权生成保存完整池、原布局/边、见证、种子、候选次序、算法版本及预算，恢复重做同一操作，成功地图直接恢复。取消并放弃进入后清票，下一次确定是新操作；同坐标重访有新的进入身份。旧会话、旧阶段、重复请求和晚到任务结果不得成为新的有效操作。

两版原生 MapSelectionSynchronizer 本来就使用独立的 map_point_selection 流，但私有流不在 RunRngSet 保存字典内，不能只用同跑局种子重建来声称恢复了位置。Mod 负责自身流的恢复，不强求匹配原版逐次抽中的玩家。

版本 Adapter 隐藏状态表示差异：public Rng 使用 uint seed/counter 与快进；beta 使用 ulong seed 与完整 SerializableRng 状态。不能只存一个 counter 套用两版，也不承诺跨版本或算法升级后同 seed 同结果。来源见 `.local/wayfinder67/rng/{public,public-beta}/`，及双版 MapSelectionSynchronizer 的构造与 MoveToMapCoord。

## 保存频率与目标版本：用户已确认

Q5 用户原话：“按你所言即可。”采用关键阶段保存、已接受编辑操作合并后台保存、正常退出等待最新完整保存完成。拿取中的预览不逐帧写盘；捕获布局时按取消语义恢复预留内容，不能为保存而释放在局玩家的实际持有。后台合并只覆盖尚未开始的编辑保存请求，已开始的写入串行完成；异常仍只恢复最近成功的完整检查点，不承诺最后一次点击必存。先古之民个人半完成奖励不增加检查点，沿用已确认的整体回退。

## Module 与 Interface

|Module|负责的复杂行为|调用者需要知道的 Interface 与时序|
|---|---|---|
|拼图跑局|Host 接受顺序、在局名单、共识、阶段、操作/进入身份；内部承载几何、持有取消、通路、可选目的地、首次节点进度、限步与追猎规则|接受玩家意图或原生结果，返回已接受状态、拒绝原因和待执行效果；请求接受不等于进入成功；调用者不需要知道规则之间的执行顺序，自动/手动共用规则并保留各自失败语义|
|布局生成|同池合格见证、确定性有界扩展、候选独立验收|输入完整原池/原布局、见证及可重放参数，输出已验候选或失败/未知；不自行替换共享图；任务结果须仍属于当前已授权操作才可提交|
|原生跑局适配|受控地图投影、进度/历史/奖励记账、房型解析、进入/完成、换幕；内部封装商店状态、服务限制、逐敌增强和专用布局|输入逻辑目标/进入身份及统一上下文，保留原生同步和事件栈，返回明确的房型/进入/必要流程结果与可保存内容；版本、遭遇与来源差异在内部 Adapter，不泄漏给几何调用者|
|检查点保存恢复|同一时刻原生与 Mod 状态捕获、串行写入、编辑合并、失败回退、同来源加载及恢复阶段分派|请求保存完整安全检查点或正常退出；保存成功才推进最近成功记录；恢复输出完整跑局与应继续操作，不能只恢复半份；优先复用原生保存与 Ritsu 载荷候选，实际路径尚需明确验证|

四个外部 Module 即拼图跑局、布局生成、原生跑局适配、检查点保存恢复。会话传输与 UI/HUD 是其输入输出 Adapter：传输不决定合法性/随机/扣步，画面不写领域状态。规则、协调、房间内容可以在 Module 内拆分，调用者不必分别协调它们。

这是职责划分，不冻结包、类或方法数量。将原生版本调用与房间/存档行为集中在实际会变化的 seam；内部可拆分测试 Adapter。删除拼图跑局 Module 会使规则与时序散回 UI/网络/生成；删除原生适配 Module 会使版本、历史、生命周期知识散回调用者，均有 Depth。避免只转发单个原生方法的浅 Module。

## 阶段与调用时序草案

1. 新幕保留原生幕/先古之民内容选择入口，但在个人奖励开始前进入拼图阶段；创建并保存原池及合格见证输入。逻辑起点独立于原生进度偏移，预算完整。
2. 编辑由 Host 接受；拿取保留原位/关联边及邻块约束，合法放下才提交新布局。未同意玩家可继续编辑，已选按钮者不编辑；在局名单与存档角色名单分开。
3. 全员同选被接受后锁定编辑，保存已授权操作及完整输入。自动开始过场并运行生成；手动按提交输入撤回孤立块再验。执行期间的迟到编辑/撤票不生效；断线不取消已授权操作。
4. 自动候选验过后才整体替换；失败保留原池/图/边并清票。手动失败保留撤回结果并清票。任务异常或取消必须先使旧结果失效，再回到允许的编辑/恢复阶段；不能把 UNKNOWN 当无解或重抽池。
5. 成功图在个人先古之民奖励开始前形成完整检查点；不能回编辑。部分个人奖励不新存半完成，退出恢复选择前玩家状态但保留成功图。全部在局必要流程完成后保存奖励及完成状态，收集共同继续；继续票不跨会话保留。
6. 探索允许已完成自己流程者先选，推进仍须所有在局必要流程结束且收齐票。Host 从票列表确定一次目的地，记录进入身份/随机结果，调用原生进入 Adapter；失败重试沿用操作，放弃则清票并终止旧身份。
7. 原生明确进入就绪后 Host 确认一次：增加探索步数、首次节点才推进原版进度；按目的地及进入前预算判定按时/耗尽。最后一步进第一/单Boss是按时，第二Boss不重判；实际房型结果归属逻辑节点。
8. 进入前的追猎状态形成根房受罚快照。从尚未追猎且剩余正步数进入、此次刚扣至0的非Boss房间及其内部事件战斗安全；已经追猎进入的房间继续受罚。仅在尚未按时抵达首Boss、额度耗尽且此前未发放时，等待全部在局必要流程/奖励结束或跳过，商店还须全队实际离开，才发面具；随后进入应用追猎。最后Boss胜利确定时先清面具再处理奖励，事件同名Boss不清，双Boss第一场不清。
9. 原生内部事件战斗/返回/服务UI只属于当前进入，不增加探索步数。完成状态由原生必要流程观测与在局名单汇合，不从关闭UI或 public RestSite.Exit 单独推导。

每次转换要么提交可恢复的完整状态，要么保留之前完整检查点。原生“进入前保存”不能被描述为新房间已进入成功；保存 Adapter 必须记录与该位置匹配的待进入状态或沿用既有完整检查点，不能提前扣步。

## 身份、传输及失败语义草案

- 逻辑节点身份在本幕池内稳定，不取空间坐标为主键。坐标只定位/绘制与几何判定；移动碎块不产生新节点。已进入商店不因重访换节点身份。
- 每次目的地确定产生进入身份，重试复用、放弃后终止；同店下一次进入使用新身份。根房内部的事件战斗使用该进入上下文加原生内部房间身份，不增加地图步数。
- 请求需关联本会话、阶段和操作身份；重建大厅后有新的会话身份，持有/投票/继续票不沿用。普通编号及明确状态足以拒绝重复和迟到，不引入自定义 hash 或冻结协议。
- 创建边与删除边是不同意图，不发送“切换有无”来处理重试；重复请求返回同一已处理结果。最后一票、撤票、断线释放和生成完成在 Host 同一接受序列交汇。
- 原生位置缓冲可能立即处理曾访问位置消息，不能承担严格的旧操作过滤。会话传输 Adapter 在交给领域 Module 前后均保留身份核验，避免旧位置消息变成新进入操作。
- 采用既有 RitsuLib 0.6.7 类型消息扩展及原生网络承载请求/已接受结果，房间执行继续保留原生同步和必要动作队列；不另建 TCP/Steam 会话，不把编辑状态偷偷写入原生坐标投票。注册/codec 已运行而 Send/Broadcast 尚未端到端验证，该部分是明确的集成验证责任，不是假定已通过。
- 纯鼠标预览可本机显示；共享占用、落点成功、清票、阶段变化以 Host 接受结果为准。客户端不据预览预测永久修改图或扣步。状态传输缺失时请求当前会话状态，不以旧事件无限补执行；不增加运行中热重连承诺。
- 生成/检查结果只有仍匹配当前已授权操作才可提交。保存恢复重新执行的任务使旧运行结果失效；确定性扩展预算是算法终止条件，不用机器耗时改变搜索候选次序。呈现等待/过场与计算任务分开，不能在原生同步等待中阻塞主线程。

## 检查点捕获与恢复草案

## 商店与其他房型适配草案

商店 Interface 按语义表达：输入逻辑商店身份、首次/重访/恢复模式和当前原生跑局，输出可供原生画面执行的真实库存；已完成的购买/补货事务可被捕获进同一完整检查点。调用者不需要知道私有字段、构造顺序、事件订阅或临时卡牌清理。

- 对所有存档原玩家保存各店货架，不只是在局玩家。未访问店没有库存，不为补齐记录提前造货。
- 记录槽位顺序、实际模型、售罄、原始基础价、促销、补货后的现货以及本店删牌 Used。牌要保留升级/附魔/原生保存属性，遗物使用其原生可保存模型状态，不简化为仅 ModelId。原版药水可按现有模型还原，额外自定义状态的第三方药水需逐来源适配。
- 动态最终价继续用当前原生价格 Hook；未使用删牌基础价按当前玩家全局删牌次数计算，再应用折扣。本店已用服务不因重访/补货恢复。
- 首次进入由原生生成货架并正常消耗对应 Shops RNG/遗物袋；重访/恢复使用已保存货架，不再 Populate 或触发 AfterItemPurchased。重建构造器若有 RNG、遗物袋或 MarkSeen 等副作用，Adapter 必须处理，不以只还原 RNG 宣称无副作用；原生事件订阅与临时悬浮牌也须正确重建/清理。
- 商店隐藏商品或禁用删牌只是受罚表现，真实货架保留。购买/删牌的发送和接收执行入口都服从根房受罚上下文，不通过伪造 Used、购买或空货架实现禁用。
- 一次购买/补货尚未结束时不捕获半份检查点；正常退出需等待事务安全结束或保留之前完整点，不能保存扣钱却未补货的中间状态。

其他房型复用原生完成/奖励生命周期，通过 Adapter 汇聚在局玩家：战斗胜利及奖励领取/跳过、事件任务与返回栈、休息实际完成（public 需额外适配）、宝箱异步开箱与全部奖励/非奖励完成；商店以全队实际离开为边界。关闭 UI、单人 Exit 或出现“可继续”按钮不是全员完成证明。事件内购物不按商店房限制，事件子战斗沿根房上下文和当前幕普通战斗增强，不重扣步。

上述库存保存与完整大厅往返尚未通过正式集成验证。参考 Mysterious Map 的 ModelId 库存方案不覆盖所有模型状态，许可证也未明确，不能复制其实现作为通用支持承诺。

建筑师面具是该生命周期在原生玩家遗物表中的实际承载，不另给每个房间维护一份追猎开关。统一进入上下文包含幕、逻辑节点、进入身份、实际房型、是否事件子战斗、是否第一/最后地图Boss及根房受罚快照。服务限制、逐敌规则、专用布局和HUD均消费它；终Boss判断不继续在各逐敌实现里猜原生空间坐标。HUD读取预算、按时结果、待发面具/追猎阶段与当前房安全状态，不能只读0步或查一个玩家的遗物推断全局阶段。

## 进度与保存的事实依据

### 原生进度：首次进入节点才推进（用户已确认）

用户原话：“首次进入节点才推进。”商店重访仍增加一次探索步数并保留完整访问及交易明细，但不推进原版内容资格的层数、不增加爬层计分。空间坐标、节点身份、每次进入身份、探索步数、首次节点进度分别表达，不共用坐标 row 或历史长度。

原生历史的奖励记账与进度消费者通过 Adapter 分工：保留实际进入的记账能力，进度/顶栏/取得层数/结算读取首次节点进度的受控投影。不能仅少加一条历史或只改 ActFloor。先古之民和换幕记账偏移保留其原生流程语义，起点仍不扣探索步数；进入新幕重置幕内进度。

对实际双版程序集进行只读 IL 交叉引用核对；精确类型导出在 `.local/wayfinder67/floor-consumers/{public,public-beta}/`。ActFloor 不等于敌人难度：NRewardsScreen 对它的判断是大于4时完成奖励教程（public 444、beta 601 行）；ActChangeSynchronizer 在全员 ready 后递增再换幕（public 68、beta 88 行），不以达到某个层数决定 Boss 完成。

TotalFloor 原生取所有幕历史条数总和，影响原生事件/遗物出现阈值、EncounterModel 生成种子、卡牌/遗物取得层数及结算 floorsClimbed 和层数分。当前 Mod 的 MindBloom 使用小于38分支，MaskedBandits 使用至少23门槛。NGameOverScreen 计分入口见上述导出 public 471、beta 650 行。

已否决让每次重访推进原版进度的替代方案：它复用原生历史计数较直接，但反复进店会推进内容门槛与爬层计分。选择首次节点进度承受额外的历史查询、奖励记账和结算适配成本。

### 保存来源的新增事实与验证责任

已读实际 RitsuLib 0.6.7 双版 Runtime DLL 与参考源码。正常路径在 ToSave 时将槽位 SerializeToNode，SaveRun 捕获具体 SerializableRun 与路径；延迟写入不会自动重新读取之后的可变槽位，不再把该泛化担忧作为缺口。

明确缺口：原生 MigrationManager.LoadSave 可选择 `.backup` 并保持原文件不变，RitsuLib AttachDocumentFromCurrentFile 却固定读取主路径。主文件缺失/无效而备份有效时，可能丢失扩展或把备份原生状态与主文件扩展混合。保存 Adapter 必须让两者跟随同一实际恢复来源。不能承诺未适配的候选库自动满足异常恢复。

精确依据：RunSavedDataPatches 的 AttachDocumentFromCurrentFile、SaveRunCapture、Canonicalize/FromSerializable 及加载响应补丁；实际 DLL 核对结果见本机 `.local/wayfinder67/`。最小验证应关联现有多人验证票：正常主文件、主文件缺失转备份、主文件加载失败转备份，加写失败不推进检查点。用 MockGodotFileIo 比较原生金币/遗物与 Mod 阶段/预算，无需真实安装或将所有联机/UI验收前置。

已[关联到多人验证票](https://github.com/Endercloud001/AllMatters/issues/68#issuecomment-6627394062)，保留其现有原生依赖与开放指派状态，不创建循环阻塞。该实验未运行。

用户最终确认原话：“确认这份方案完整，可按原约定发布 resolution、更新父地图并关闭本票”。按此授权发布并审视剩余开放票和 Not yet specified；本票完成不代表父地图结束，不直接进入正式开发。

不另建 ADR：这些选择及替代方案已在本决策票与记录中解释，尚未形成需要跨出本次决策记录单独维护、且成本足够高的额外不可逆决定；避免重复保存同一结论。

# AllMatters 反馈功能实机验收

本功能依据《反馈规格文档》实现。验收目标为本地开发副本 public v0.107.1 与 public-beta v0.113.1，分别使用完整 RitsuLib 0.6.11 variant-pack 的对应兼容分支。Steam 后续更新的版本需要另行核实兼容性。

## 安装

两目标测试包分别由 `tools/Build.ps1` 输出到本功能树的 `dist/public/AllMatters/` 和 `dist/public-beta/AllMatters/`。包内文件为 DLL、PCK、manifest、LICENSE 与 THIRD_PARTY_NOTICES.md。用户按自己的实际游戏版本选择其中一包，退出游戏后将五个文件更新到 `mods/AllMatters/`，完整安装 RitsuLib 依赖后通过 Steam 启动。

本机依赖来源为主仓 `.local/dependencies/RitsuLib-0.6.11/`，需要完整 variant-pack 目录结构。此次实现沿用既有依赖版本，游戏安装和启动由用户执行。

## 操作与预期

1. 主菜单进入游戏设置 → 发送反馈。展开 Category，确认 `For AllMatters` 只有一项。选中后按钮显示 `Export`，切回普通类别后恢复原版发送文案。
2. 保持文字为空，点击 Export 并连续点击数次。应只生成一份报告，成功弹窗精确显示“诊断文件已生成完毕。请将此文件发给模组作者。”，文件管理器打开游戏可执行文件所在目录并尽可能选中文件。
3. 检查文件名为 `AllMatters_diagnosis_pack_YYYY-MM-DD_HH-MM-SS.zip`，时间使用本机时间。同秒已有同名文件时，再次导出应提示稍后重试，原文件仍能打开。
4. 解压报告，确认存在 `feedback.txt`、`environment.json`、`context.json` 和 `collection.json`。空文字对应空的 feedback.txt。当前和上次运行日志分别位于 `logs/current.log` 与 `logs/previous.log`，缺失的日志在 collection.json 留有原因。
5. 填入可识别的测试文字，再次导出，检查文字进入 feedback.txt。文本中的当前用户主目录及符合原生规则的 SteamID64 经过 LogSanitizer 处理，JSON 类型应完整。图片中的其他敏感信息由玩家在提交前自行检查。
6. 进入一局，从暂停菜单导出。检查 context.json 的种子、角色、进阶、楼层等与当前局面相符；有现存局内存档时，attachments 内包含对应存档副本。该副本反映游戏此前已落盘的保存点。
7. 导出期间关闭反馈界面并返回游戏。任务应继续，完成后仍显示结果。再次打开界面，文字和类别应保留，Export 可继续使用。用手柄重复选项切换和导出。
8. 失败场景在可恢复的测试环境中验证。目标目录不可写时应显示失败原因，保留文字和类别，恢复 Export；文件管理器打开失败时，仍显示生成成功及可复制的文件路径。
9. 每次正常成功或已处理失败后，检查游戏目录只有本次最终 ZIP；此前成功报告保留。进程意外退出留下的本功能 `.partial` 文件在下次启动清理，其他存活游戏实例正在写的文件应保留。

## 附件和证据边界

自动导出覆盖现有局内存档和局内反馈时原生界面提供的截图。主界面反馈跳过默认截图，没有其他适用附件时 ZIP 中没有附件条目。当前缺少可直接复用的最近 AllMatters 异常缓存，联机分歧 ZIP 的会话归属和内部格式也尚未核实，这两项在 collection.json 明确记录跳过原因。

自动化界面测试使用真实类别资源、原生按钮和引擎输入事件，补齐无界面宿主的控制器及开发控制台实例，替代反馈屏幕装饰初始化和结果展示出口。测试覆盖空文本、重复事件、隐藏及真正释放来源界面后的任务完成；原生成功弹窗、系统文件管理器、手柄物理输入和正式游戏加载由以上实机步骤验证。

# Wayfinder：项目执行流程

本页只约束 AllMatters，不修改全局 wayfinder skill。地图、票据类型、领取与原生依赖操作沿用 [issue-tracker.md](issue-tracker.md)。本页组织每张票的执行、证据和交接；它不增加审批层级。

## 1. 定位与准备

先确认仓库/工作树、分支及现有修改，再读 AGENTS、父地图、目标票全文及评论、相关规则最新修订。首次读取保留完整结果，后续只查发生变化的部分；每次远端写入前重新读取目标，保留并发修改。

新工作树先运行 `tools/InspectWorktree.ps1`。它只报告路径、工具和附近 Godot 候选，不改配置。结合 `docs/development.md` 补齐本次实际需要的依赖；逻辑原型不自动要求完整游戏构建。复用已有 Paths.local.props 时，将其中相对路径按来源目录解析，并保留当前配置已有值；本机值只写 Git 忽略的本工作树配置。先做一次最小运行，再把环境问题报告为阻塞。能从本机查到的事实由 Agent 查，不要求用户重复提供。

资产入口从来源票查找，至少包含：分支、提交、仓库内路径、运行命令、已验证范围。已有演示仅在个人可视化目录时，先把所需源码/数据放入本票原型分支并留下来源指针，避免下个会话重新遍历个人目录。

## 2. 要求与完成判据

开工时把本票要求映射为一张证据表：要求ID、负责方（Agent/用户）、状态、证据、下一步或阻塞原因。需求正文仍在来源票；表中引用它，不复制完整规则。可将表保存在原型的实验记录中，由工具生成展示，见 [prototype-tools.md](prototype-tools.md)。

- 有可继续的 Agent 工作时，进度汇报后继续执行。补代码、补实验、核对环境和整理原始记录都不能被转交成“等用户体验”。
- 需要用户选择规则/体验取舍时用 grilling，明确当前问题；继续所有不依赖该答案的 Agent 工作。剩余 Agent 项确实依赖用户时，列出依赖再等待。
- Agent 部分完成：本票要求的自动工作已满足，或已明确交给其他票且本票允许该边界；不能用页面可打开、测试通过或一次构建替代逐项证据。
- 用户部分完成：用户实际参与并明确通过相应场景。自动测试不会推导出用户通过。保留部分场景已通过的反馈，只重开受后续变更影响的部分。
- 可 resolution：Agent 与用户部分均满足本票范围，未把其他票承担的实机/网络验证反向扩大为本票关闭条件。收口审查沿用 [review.md](review.md)。

报告生成工具只帮助发现记录缺失，不替代用户判断、票据类型或 GitHub 原生依赖状态。

## 3. 先小样本，再全量

先复用已有资产，打通真实的一条链：原输入 → 运算 → 独立验收（若本票需要）→ 提交成功结果或恢复失败状态 → 页面反馈。批量实验和体验页面复用这条链；记录回放明确标注用途，不替代实时等待或执行中恢复。

每配置先跑少量种子（通常3–5个），覆盖最小/最大预算、关键负例、异常和恢复。先测一个最重档位，确认成本、计数和失败出口，再跑票据要求的完整矩阵。计时注明输入准备/构造、搜索、独立验收、替换和页面等待，区分冷启动与常驻进程；内存注明采样对象和峰值/增量范围。毫秒测量不自动升级为玩法规则。

原型目录配置 `prototype.json` 的轻量 smoke 入口，运行 `tools/CheckPrototype.ps1`；完整种子矩阵由显式命令运行，不塞入默认 smoke 或每次推送。长实验的脚本应支持单独输出目录，以普通算法版本、参数、种子集和运行状态标明一次运行。源码或输入改变后启动新轮次，保留中断原因；报告只引用明确完成的轮次。无需另加自定义 hash、冻结接口或结果基线。

## 4. 规则变更

先澄清会改变实现含义的边界，例如 Boss 替换前后、骨架共边还是固定内部边。用户确认后按此顺序处理：

1. 在规则来源票的 resolution 修订中记录完整决定；父地图只更新名称链接及摘要。
2. 列出受影响的输入池、构造见证、验证器、保底/恢复、场景和实验记录。
3. 将失效证据标为历史或拒绝负例；运行时继续使用原输入，不能为适配新算法修复、换池或降低规则。
4. 更新实现，先跑针对性正反例及小样本，再跑受影响矩阵；区分完整布局检查与单个验收阶段检查。
5. 更新证据表；保留未受影响的用户通过反馈，邀请体验确实改变的场景。

涉及生成规则、独立验证和给定池恢复时，要同时覆盖正常成功、预算零/耗尽、异常和执行中恢复。不要只改常规成功路径。

## 5. 证据与工具输出

实验输入/算法版本/运行参数从记录读取，结果从原始输出汇总。用户批准状态只有一个记录入口，报告读取该状态；不要在多个 Markdown 和报告生成器中分别硬写 passed/pending。状态变更使用用户原话或来源链接，不用测试结果代填。已有原型继续使用自己的实验记录格式，不为套模板复制第二份状态。

每组输出样本数及实际验证范围，区分不同池、同池不同种子和重复布局；找到解、完整穷尽和预算内未知分别统计。检查脚本应对漏组、退出码丢失和报告与源记录不一致给出明确错误，这些用普通类型检查与测试处理。

检索先用 rg，输出限定路径、行号和必要字段。含内嵌图片的HTML按脚本区段/JSON字段读取，或用 `tools/ReadTextSlice.ps1` 返回限定长度的匹配片段。完整工具响应和日志留在本地，避免把同一大结果反复塞回上下文。工具方法首次按任务筛选，后续复用已知接口，不列出整个工具目录。

## 6. 验收与一次收尾

先更新唯一的用户状态记录，再生成报告并检查一致性。核对证据表所有本票项、命令、原始记录、分支/提交、已知边界及用户原话，然后集中提交推送。查看检查汇总和远端分支是否一致；提示型 pre-push 允许推送，不代表检查通过。保留现有检查和安全措施。

发布 resolution → 关闭本票 → 更新父地图 Decisions so far 的一行摘要 → 向集成票提供结果与边界 → 核实剩余原生依赖。只处理本票，不顺手关闭其他验证票或预选架构。原型资产留在独立分支；游戏启动、安装与正式发布继续按现有项目要求处理。

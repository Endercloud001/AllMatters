# 游戏机制与展示审查

本页供 reviewer 在审查卡牌、能力、事件或展示改动时使用。机械错误交给现有编译和普通测试；本页保留需要结合需求与调用链判断的事项。

## 展示是否表达真实变化

对文案改动，比较未升级、已升级、升级预览三个状态，以及已支持的语言。绿色范围应对应实际新增或改变的内容；效果整段改变时整段高亮可以合理，不机械禁止某种 IfUpgraded 写法。

区分“未升级牌的升级预览”和“已升级牌在单卡界面查看升级”：二者都可能走预览路径。你好世界现有 UpgradePreviewHighlight 测试覆盖中英文的这两种状态，同时保留普通牌原文及非预览显示。

## 机制依据是否足够

从 [机制阅读地图](../game-mechanics.md) 定位调用链，检查实现是否保留本次需求相关的归属玩家、快照时机、可变实例、原版池、RNG 及命令副作用。方法名或签名相同只能支持 API 判断，不能证明两分支内部行为一致。

新增依赖或替换原版流程应对应真实需求和已经查明的接入限制；框架提供接口并不等于当前功能需要引入框架。具体分支差异和取舍应在功能验证记录中可找到。

## 测试证据是否覆盖当前行为

查看测试宿主替代了哪些边界。现有宿主替代全局进行中状态和空手通知；如果新需求依赖这些通知、完整房间调度或网络生命周期，原宿主的通过结果不足以覆盖该行为，需要实际场景或明确的待验证说明。

公开接口测试、目标 DLL 编译、正式 Mod 加载、用户实机截图、真实联机及回放是不同证据。报告只陈述已执行的范围；用户确认的功能验收与尚待执行的发布验证分别记录。
